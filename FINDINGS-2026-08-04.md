## 🔴 1. `verify.sh` misses directory-source marketplaces → reports all 10 OF1 skills missing

**File:** `skills/of1-check-dependencies/scripts/verify.sh` (~line 63)

`SKILL_ROOTS` was a fixed list of four paths:

```
$HOME/.claude/plugins   $HOME/.claude/skills   $PWD/.claude/skills   /workspace/skills
```

Claude Code also supports marketplaces added from a local directory
(`/plugin marketplace add <path>`), whose `installLocation` is that directory — outside all four
roots. Our own dev checkout is installed exactly that way:

```json
"of1-demo-skills": { "source": { "source": "directory", "path": "/Users/…/labs/of1-demo-skills" } }
```

Result: **all 10 OF1 skills reported missing** with a misleading fix hint
(`/plugin install of1-demo-skills@<marketplace>`) even though they were correctly installed and
working. Hard-fails the pipeline at Phase 0.

This hits **every developer testing from a local checkout** — i.e. the whole dev loop.

**Fix applied (uncommitted, in working tree):** also read `installLocation` values from
`~/.claude/plugins/known_marketplaces.json` into `SKILL_ROOTS`.

**Still to decide:** whether to also make the failure message smarter (e.g. "found 0 of 10 —
is this a local checkout?"), since a wall of 10 missing skills reads as a broken install rather
than a broken detector.

## 🔴 2. Adopt-site's CC dispatch model is impossible: subagents cannot spawn subagents

**Files:** `skills/of1-adopt-existing-site/SKILL.md` (§ Dispatch → Claude Code, lines ~118–131)
and `skills/of1-demo-orchestrator-cc/SKILL.md` (§ Phase 2, HARD RULE)

The two skills contradict each other on Claude Code:

- `of1-demo-orchestrator-cc` says Stage 3 must be **a single `Agent` delegation** to
  adopt-site, and adds a *HARD RULE*: "do NOT re-implement steps 6–12 here."
- `of1-adopt-existing-site` then says each of its ~14 steps "is a single `Agent` dispatch" and
  "**Parallelism is mandatory** at each fan-out point — dispatch all eligible Agents in a single
  message."

But in Claude Code the `Agent` tool is **withheld from subagents** — nesting is capped at one
level. So adopt-site, running *as* a subagent, has no `Agent` tool and cannot fan out at all.
It silently degrades to running 14 steps sequentially in one context.

Observed in this run: the dispatched Stage 3 created its own TaskCreate entries and started
working through 8a → 8b one at a time. Confirmed the degradation is real, not theoretical.

Consequences: loses the 5-way fan-out (6-base/7/8a/8b/10) and the 5-way intent fan-out (6a–6e);
concentrates ~14 steps' work into one context window; materially extends wall-clock (which in
turn raises the risk of the DA token expiring mid-run).

Note this design is coherent on **SLICC**, where `scoop_scoop` nests. The bug is specifically the
CC column.

**Options:**
1. Orchestrator owns steps 6–12 directly on CC (drop the HARD RULE + single-delegation for the
   CC path). Restores full parallelism; costs the clean Stage-3 encapsulation.
2. Keep the delegation but have adopt-site detect "no Agent tool" and document that CC runs
   sequentially — honest, but forfeits the parallelism the skill calls mandatory.
3. Split adopt-site into a thin CC-orchestrator half plus step definitions the top level dispatches.

**Chosen for this run:** option 1, at the user's direction — stopped the Stage 3 agent and took
over the fan-out from the top level.

**Salvage note:** the stopped agent's step-8a output (`of1/config/brand-voice.json` + status file)
was complete and reusable — no re-run needed. Good sign that per-step state files make the flow
restartable. Step 8b was mid-flight and had written nothing, so it was cleanly re-dispatchable too.

## 🔴 3. `of1-check-dependencies` assumes the repo is already onboarded to AEM

**File:** `skills/of1-check-dependencies/SKILL.md` (§ Part 2, step 4 "Code Sync check")

`verify.sh` checks the repo is *structurally* an EDS repo (has `scripts/aem.js`, `styles/styles.css`
etc.) but never checks whether the repo has an **AEM site config**. Part 2's Code Sync check then
just curls the preview URL and, on non-200, sleeps up to 150s and emits a soft `WARN` before
continuing.

For our fresh repo there was **no site config at all**:

```
GET admin.hlx.page/config/of1-labs/quentin-test-skills-v5.json → 404
GET main--quentin-test-skills-v5--of1-labs.aem.page/styles/styles.css → 404
```

No amount of waiting would ever fix that, so the skill would have proceeded past a soft warning
into a pipeline that cannot possibly render — the failure would surface much later, in a replica
or deploy step, far from the cause.

**Fix applied manually (not yet in the skill):**
1. `POST admin.hlx.page/config/of1-labs/sites/<repo>.json` with the `content.source` (DA markup URL)
   + `code.source` (GitHub) shape copied from a working sibling site.
2. `POST admin.hlx.page/code/<owner>/<repo>/main/*` to force the initial sync — Code Sync had
   never fired for this repo because the config didn't exist when the last push happened.

After that, `styles.css` and `aem.js` served 200 immediately.

**Recommended skill change:** check for the site config explicitly; if absent, either create it
(preferred — it's a single authenticated POST and this will recur for every new demo repo) or hard-fail
with the exact remediation. Also: after creating a config, always force a code sync, because Code
Sync only reacts to *pushes* and a just-configured repo has none pending.

**Related sharp edge:** a 404 on `/` is *expected* for a config-less-but-correct repo (no content
in DA yet), so `/` is a bad liveness probe. Probe a **code** asset (`/styles/styles.css`) instead —
that isolates Code Sync from content state. Worth encoding in the skill.

## 🟠 4. GitHub App installation probe gives false negatives

Not a skill bug — a diagnostic trap worth documenting for whoever debugs this next.

`gh api /orgs/<org>/installations` shows `aem-code-sync` with `repository_selection: "selected"`,
which *suggests* checking whether our repo is in the selection. But
`GET /user/installations/<id>/repositories` 403s with an OAuth-token scope error. Piping that
failure into `grep -x <repo>` yields no match, which reads as "NOT SELECTED" — a false negative.
Code Sync was in fact installed and working, as the user confirmed and the forced sync proved.

**Lesson:** don't infer app-installation state from that endpoint under `gh`'s default token.
Test the capability directly instead: `POST admin.hlx.page/code/<owner>/<repo>/<branch>/*` and see
whether a job is accepted.

## 🟠 4b. Product image URLs are 301s — liveness checks must follow redirects

**Files:** `skills/of1-extract-content` (and any skill/step that verifies asset URLs)

Step 8b reported "verified every image URL returns HTTP 200 on
`main--…aem.page/media/…`". On check, **all 68 images return `301`** on the first hop, redirecting
to a content-hashed DA path:

```
/media/product-house-blend-dark-roast-1.png
  → 301 → /media/media_1469ed3d29ccccee2d019cecaf327b6d5b2b6fe9f.png → 200 image/png 2.5MB
```

Following redirects, all 68 do resolve 200 with real bytes — so the *outcome* was correct, but the
claim wasn't literally true. Any verification step doing a non-following `curl`/HEAD will see 3xx
and could either falsely fail, or (worse) treat 3xx as success and never confirm bytes exist.

**Recommended:** every asset liveness check in these skills should use `curl -sL` and assert the
*final* status is 200 (ideally also `content_type` starts with `image/` and `size_download > 0`).
Worth stating in the skill so agents don't report first-hop status as if it were final.

**Also worth noting:** a 2.5MB PNG for a product image is heavy for an EDS demo that's supposed to
target a PageSpeed score of 100. If images are uploaded verbatim from the source, consider whether
the skill should flag oversized assets.

## 🟠 4c. `products.json` shape is undocumented and counter-intuitive

`of1/config/products.json` is a **bare JSON array**, not the `{"products": [...]}` envelope the
filename and the other config files suggest. The obvious first probe (`jq '.products | length'`)
errors with `Cannot index array with string "products"`.

Per-item keys (from this run): `id, name, category, currency, description, features, highlights,
images, keywords, persona, price, url, useCase`.

Cross-reference keys used by the sibling files are also non-obvious and inconsistent between files:
`personas.json`/`use-cases.json` → `recommendedProducts`; `features.json` → `productIds`;
`faqs.json` → `relatedProducts`. Three different names for the same relationship.

**Recommended:** document the exact shape of each config file (a short schema block in the skill,
or a JSON Schema in the repo), and consider unifying the three ref key names. Undocumented shapes
mean every downstream consumer — and every reviewer — has to reverse-engineer them.

Stage 1 excluded `/coffee`, `/machines`, `/quiz` because they're Commerce-dropin GraphQL renders

could lead a downstream stage to skip data it could actually get.

## 🔴 4e. `products.json` carries a known-404 URL on 3 SKUs

**File:** `skills/of1-extract-content` (output: `of1/config/products.json`)

Step 8b assigned every product a category-page `url`. Distribution:

| url | SKUs | live status |
|---|---|---|
| `https://frescopa.coffee/accessories` | 5 | 200 |
| `https://frescopa.coffee/coffee` | 6 | 200 |
| `https://frescopa.coffee/machines` | 3 | 200 |
| `https://frescopa.coffee/tea` | 3 | **404** |

The three Tea SKUs (Sunrise Meadow, Mystic Serenade, Twilight Bliss) point at `/tea`, which
**Stage 1 had already identified and recorded as a live 404** in `narrative.json.excludedPages`.
The information needed to avoid this was sitting in a file the step read.

This is a demo-visible defect: OF1 will happily recommend a tea and link the user to a 404. It also
compounds finding #8/#11 — `excludedPages` is being treated as advisory rather than as a constraint.

Two things to fix:
1. `of1-extract-content` should validate every `url` it emits (`curl -sL`, assert final 200) and
   either drop the field or fall back to a known-good page when it fails.
2. It should cross-check emitted URLs against `narrative.json.excludedPages` and never emit one
   that Stage 1 already flagged as 404.

Also: assigning a *category-page* URL to a specific SKU is questionable even when it returns 200 —
`/coffee` is not a product detail page, so "learn more" lands the user on a grid. Worth deciding
whether `url` should be omitted when no real PDP exists.

## 🟡 4f. Step summaries overstate what was produced

Step 9's own status summary read:

> "Generated 12 suggestion chips (deep-dive, comparison, recommendation, discovery, budget) …"

which implies five distinct `type` values. The actual file has `"type": "explore"` on all 12 —
**which is correct**, because the skill mandates it (`suggestions[].type` → always `"explore"`).
The intents were varied in the *queries*, not the types. So the artifact is right and the prose is

Same class of thing as #4b (first-hop 301 reported as "200"). Individually trivial; collectively they

of pipeline state. **Recommendation:** the output contract should ask for summaries phrased in terms
of the fields actually written, and orchestrators should verify artifacts rather than accept
`status: done` at face value. (In this run, every accepted step was independently verified — that's
how #4b, #4c and #4e were caught.)

**Skill:** `stardust:replica` (adobe-skills plugin, not ours — but it breaks our demo repo)

## 🟠 4h. `DESIGN.json` written to repo root, but adopt-site looks in `stardust/current/`

**Files:** `stardust:replica` (writer) vs `skills/of1-adopt-existing-site/SKILL.md` line ~42 (reader)

Adopt-site's Phase 1 artifact detection is:

```bash
[ -f stardust/current/DESIGN.json ] && HAS_DESIGN_JSON=true
```

`stardust:replica` actually wrote it to the **repo root**: `./DESIGN.json` (alongside `DESIGN.md`
and `PRODUCT.md`), with valid content:

```json
{ "writtenBy": "stardust:replica", "mode": "bounded-single",
  "writtenAt": "2026-08-04T10:10:24Z", "againstInput": "https://frescopa.coffee" }
```

`stardust/current/DESIGN.json` does **not** exist. So adopt-site's detection would report
`HAS_DESIGN_JSON=false` and dispatch Step 3 to re-run `stardust:extract` — wasting an expensive
Opus extraction step to regenerate a spec that already exists one directory up.

Note adopt-site explicitly anticipates `_provenance.mode: bounded-single` as valid input
("do NOT reject or re-extract on a bounded-single spec") — so the *intent* is clearly to consume
exactly this file. It just looks in the wrong place.

**Recommended:** adopt-site should check both locations (`stardust/current/DESIGN.json` and
`./DESIGN.json`), or the two skills should agree on one canonical path. This is a silent
efficiency/correctness bug — nothing errors, you just pay for a redundant extraction and may end
up with two divergent specs.

**Blast radius is wider than adopt-site.** Verified `grep -rln "stardust/current/DESIGN"` across the
plugin — **four** skills hardcode that path, and all four are *consumers* that would silently read
nothing on a `stardust:replica`-produced repo:

| Skill | Use |
|---|---|
| `of1-adopt-existing-site` | Phase 1 artifact detection → wrongly triggers a redundant Step 3 |
| `of1-build-templates` | line 181 — token source for `styles/of1-template-base.css` |
| `of1-style-generative-block` | lines 38, 71–72 — brand tokens for the OF1 block |
| `of1-build-cta-template` | design tokens for the CTA |

The three consumers don't error on a missing file; they fall back to guessing tokens from
`styles/styles.css`, so the failure mode is **off-brand output with no warning**. In this run I had
to hand-inject "the spec is at `./DESIGN.json`, not `stardust/current/`" into all three step-6/7/10
dispatch prompts to avoid it. The fix should be a single shared resolver (check
`stardust/current/DESIGN.json`, then `./DESIGN.json`, and **fail loudly** if neither exists) rather
than four independent path literals.

### Related: `of1-build-templates` hard-references prototypes that never exist in this flow

Same class of problem, same skill. `of1-build-templates` lines 49–50, 144–148, 163, 176–183 treat
`deliverables/prototype-*.html` and `deliverables/eds-prototype-*.png` as the "canonical token
source" and "visual ground truth". Those come from a step 4 that **the pipeline path taken here
never runs** — `stardust/prototypes/` was empty (verified: 0 files). The skill does document a
fallback for exactly this case (line 51, line 185: "If no prototypes exist — e.g.
`of1-adopt-existing-site` against an existing EDS site"), so the logic is present, but the *emphasis*
is inverted: ~10 lines instruct "read every prototype, they are ground truth" against 2 lines of
fallback. An agent reading top-to-bottom is likely to hunt for prototypes, and `ls
deliverables/prototype-*.html` failing is easy to misread as a blocker. Recommend hoisting the
`HAS_PROTOTYPES` branch to the top of the inputs section so the no-prototype path is a first-class
mode rather than a footnote.

### Related: `of1-style-generative-block` chrome path was correct here

Line 231 / line 352 reference `content/nav.html` and `content/footer.html`. Verified these **do**
exist in this repo (`content/{nav,footer,index,subscription,sustainability}.html`, written by the
replica's deploy phase) — so no defect. Noting it because the repo *also* carries
`drafts/*.plain.html`, and I initially warned the step-7 agent the chrome was drafts-only. Two
parallel copies of the chrome in different formats is a latent trap for a skill that hardcodes one.

## 🟠 4i. No resumability after an infrastructure failure mid-stage

Stage 2 died at ~12:27 with `API Error: Stream idle timeout - no chunks received` — an
infrastructure failure, not a skill bug. But it exposed that **`stardust:replica` has no resume
story**: it's a 5-phase skill (capture → preserve/register → recreate → fidelity gate → migrate/deploy)
whose only completion signal is the orchestrator-supplied `replica-done.json`. There is no per-phase
status file, so from the outside you cannot tell what finished.

I had to reconstruct progress by hand from filesystem archaeology:

| Evidence | Inference |
|---|---|
| `stardust/current/pages/{index,subscription,sustainability}.json` | capture done |
| `stardust/replica/capture/tokens.json`, root `DESIGN.json`/`DESIGN.md` | preserve/register done |
| `drafts/{index,subscription,sustainability,nav,footer}.plain.html` | recreate done |
| `stardust/replica/gates/{index,subscription,sustainability}-{360,1440}/{live,proto,diff}.png` | gate **ran** at both breakpoints |
| no verdict file; `stardust/replica/inconsistency-register.md` present | gate outcome **unknown** |
| DA list empty | migrate/deploy **not** done |

The gate produced diff images but recorded no machine-readable verdict, so whether it *passed* is
unknowable without re-running or eyeballing 18 PNGs.

**Recommended:** every multi-phase skill should write `stardust/replica/phase-<N>-status.json` (or
similar) as it completes each phase, and the fidelity gate specifically should persist a verdict
(pass/fail + per-page/per-breakpoint scores). Without that, any mid-run crash forces either a full
restart (expensive — this stage had ~55 min of work in it) or manual forensics like the above.

## 🔴 4j. The fidelity gate can pass on a self-comparison (false PASS)

**Skill:** `stardust:replica` (upstream) — found by the resume agent, verified by it in detail

The first Stage 2 run's gate evidence was **invalid in two independent ways**, and it still produced
a PASS:

1. **Self-comparison.** `gates/index-1440/live-real.png` and `proto-real.png` were *both prototype
   captures* — identical 3098px height, neither containing the live-only Sign-in affordance. The gate
   compared the prototype against itself and reported a 5.11% PASS. A gate that can compare an
   artifact to itself and pass is worse than no gate: it manufactures false confidence.
2. **Degraded live source.** `stitch-shot.mjs` inherits `diff/live-session.mjs`, which sets
   `Upgrade-Insecure-Requests: 1` as a context-wide header. On frescopa.coffee that header alone
   breaks the offer content-fragment's client-side fetch, so the live page renders a raw DAM path and
   measures 2964px instead of 3098px. The resume agent bisected header-by-header to isolate it.
   The skill's own hardening rule 12 says a degraded source must never be measured — so the gate
   violated its own rule.

Fix applied by the resume agent: live captures now go through `scripts/replica/_live-shot.mjs`
(UA-only context, otherwise mirroring stitch-shot). Corroborated by all three live heights now
matching the extract-phase `crawl.mjs` screenshots exactly.

**Recommended (upstream):** (a) the gate must assert the two inputs are provably different sources —
e.g. tag each capture with its origin and refuse to diff same-origin pairs; (b) don't set
`Upgrade-Insecure-Requests` on live capture contexts; (c) validate live capture height against the
extract-phase screenshot before measuring, and fail loudly on mismatch.

This is the most serious finding of the run: combined with #19 (no machine-readable verdict), a
false PASS is invisible. Only a fresh agent distrusting the prior evidence caught it.

## 🔴 5. Token expiry: DA deploy blocked mid-pipeline (now realized, not hypothetical)

Finding #5 below was written as a 🟡 risk. **It came true and blocked the pipeline.** Upgrading.

Timeline:
- Token `created_at` 11:17:31, `expires_in` 10800000ms (3h) → hard expiry **14:17:31**
- Stage 2's resume agent reached migrate/deploy at ~15:07 → **~50 min past expiry**
- Every `admin.da.live` and `admin.hlx.page` call now returns **401** (confirmed independently)

**The root cause was my arithmetic, not a bad API.** Both sources agree; I misread the number.

- At 12:33, `/profile` returned `ttl=6368s` → 12:33 + 6368s = **14:19:08**
- JWT `created_at + expires_in` → **14:17:31**
- The two agree within ~2 minutes.

My error: I reported `ttl=6368s` as "~106 minutes **left**" — correct — but then treated that as
comfortably covering the rest of the run without ever converting it to a wall-clock **deadline**.
106 minutes from 12:33 is 14:19, and the remaining work ran past 15:00. A relative duration invites
exactly this mistake; an absolute timestamp does not.

Both `/profile.ttl` and the JWT claims are reliable. The fix is presentation, not source selection:
**always print the absolute expiry time**, and compare it against an estimated completion time.

**Follow-up (15:42, second token):** re-probed both sources on the replacement token.
`admin.hlx.page/profile` returned **`ttl: null`** with no `email` field, while the JWT decoded
cleanly to `17:33:54` and a live `admin.da.live/list` call returned **200**. So `/profile.ttl` is
*not* dependably populated — it was present on the first token and absent on the second. Refining
the recommendation: **decode the JWT (`created_at + expires_in`) as the primary source** and treat
`/profile.ttl` only as a corroborating signal when non-null. A liveness probe against
`admin.da.live/list/<owner>/<repo>` is the cheapest authoritative "is it still good right now" check.

Implementation note for whoever fixes this: `base64 -d` fails on the JWT payload because Adobe's
claims segment is unpadded base64url. Use `base64.urlsafe_b64decode(p + '=' * (-len(p) % 4))` —
naive `cut -d. -f2 | base64 -d` produces truncated JSON and a parse error.

**Recommended:** `of1-check-dependencies` should print the **absolute wall-clock expiry time** (from
either source — they agree), e.g.

```
✓ DA token → …/.hlx/.da-token.json (expires 17:33:54, in 124 min)
```

and refuse to start, or loudly warn, when expiry lands before the expected pipeline finish (~2h out).
Never report a bare relative duration — that's precisely the framing that caused this failure.
Additionally, every step should treat a 401 as an explicit token-expiry failure (this run's dispatch
prompts did instruct that, and it worked: Stage 2 reported cleanly instead of silently degrading).

A pipeline that dies ~90 minutes in on a foreseeable credential expiry is the most expensive failure

## 🟡 5-orig. Token expiry is unmanaged across a long pipeline (original text, superseded by #5 above)

The DA/IMS token is captured once at Phase 0 and passed to every stage. This run's token had
~2.6h of life; a full three-stage run can approach that, and the Stage-3 restart burned more.
Nothing in the pipeline checks remaining TTL or refreshes.

The token payload carries `expires_in` + `created_at`, and `admin.hlx.page/profile` returns a live
`ttl` — so this is checkable. **Confirmed working in this run:**

```bash
curl -s -H "Authorization: Bearer $T" https://admin.hlx.page/profile \
  | jq -r '.profile | "ttl=\(.ttl)s (~\(.ttl/60|floor)min)"'
# → ttl=6368s (~106min)
```

Note the live `ttl` is the authoritative figure and was **much more generous than the JWT
`created_at + expires_in` arithmetic suggested** — mid-run I wrongly believed the token was
expiring immediately based on the JWT claims, when 106 minutes remained. So the skill should read
`/profile`'s `ttl`, not compute from the JWT.

**Recommended:** have `of1-check-dependencies` report remaining TTL and warn when it's below some
threshold (say 3h) at Phase 0, so the operator can refresh *before* a 90-minute run instead of
discovering it at the deploy step. Individual step prompts should keep reporting 401/403 as explicit
token-expiry failures (this run's dispatches were told to, and that instruction is worth folding
into the skills themselves).

## 🟠 6a. Steps 6-base and 10 reported `done` but left their deliverables uncommitted

Both agents wrote a correct `status: done` status file and then went idle **without committing**:

| Agent | Deliverable | Git state when it went idle |
|---|---|---|
| 6-base | `styles/of1-template-base.css` | **untracked** (`??`) |
| 10 | `of1/config/cta-template.json` | **staged, never committed** (`A `) |

For 6-base this is arguably correct-by-design — `of1-build-templates`' race-safety section says the
`assemble` phase owns git, and `base`/`intent` modes deliberately don't commit. But the skill never
says so in the `base` mode section itself, and the agent's own summary ("Generated
styles/of1-template-base.css with brand tokens") reads as complete. An orchestrator that trusted
`status: done` and moved to deploy would ship a demo whose every per-template stylesheet `@import`s

extreme, because the next agent that runs `git commit` sweeps up someone else's file under its own

prevent, reached by a different route.

**Recommended:** every step skill should end with an explicit, unambiguous git contract — either
"commit and push these exact paths" or "do NOT touch git; phase X owns it". Where a step must not
commit, say so in that mode's own section, not only in a race-safety note further up. And no step
should ever leave staged-but-uncommitted changes; if it stages, it commits.

This is finding 15's twin: the summary was accurate about *content* and silent about *state*.
Verifying artifacts exist isn't enough — an orchestrator has to verify they're **committed**.

## 🟡 6c. Deploy contract's "exactly one `<h1>`" assert conflicts with replica fidelity

Stage 2's deploy agent hit the deploy contract's "exactly one h1" assertion and waived it. I verified
the claim independently rather than accepting it — `curl -sL | grep -c "<h1"` across both origins:

| Page | live frescopa.coffee | our replica |
|---|---|---|
| `/` | 0 | 0 |
| `/subscription` | 0 | 0 |
| `/sustainability` | 0 | 0 |

The waiver was correct. frescopa.coffee genuinely ships no `<h1>` on any of these pages, so the

**Note for the OF1 layer (different rule, same fact):** this only applies to *replicated* pages. The
OF1 templates and `/of1` are **new** pages, not captured content, so they should each carry a proper

an explicit line in `of1-build-templates`/`of1-style-generative-block` so agents don't infer "this
site has no h1" from the surrounding replica and propagate the source's SEO weakness into new pages.

## 🔴 6d. Budget-intent templates invented a subscription pricing structure that does not exist

**File:** `templates/of1-budget-price-tiers.sample.json` (+ `of1-budget-roi-story.sample.json`)

The budget agent authored a three-tier subscription plan as sample data:

| Tier | Price | Status |
|---|---|---|
| Starter | `$3.99 / cup` | price is real (pod price) but mislabeled as a per-cup plan rate |
| Everyday | `$14.99 / month` | **$14.99 is a *bagged coffee* price, not a subscription price** |
| Enthusiast | `$29.99 / month` | **fully invented** — not in the catalog at any price |

Plus derived stats: `$0.50` average cost per cup, and in `roi-story` a 12-month arc asserting "a year
of MyBarista costs about **$180**" / "roughly **$90** spent" at month 6.

**Verified against ground truth, both sources:**
- `jq '.[].price' of1/config/products.json` → `3.99 4.99 7.99 9.99 14.99 39.99 299 399 499`. **$29.99
  is absent.** Categories are Accessories / Bagged Coffee / Coffee Machines / Coffee Pods / Tea —
  **there is no subscription product at all.**
- Fetched the live `https://frescopa.coffee/subscription` and stripped tags: the page publishes
  **zero prices and zero tier names**. No "Starter", no "Everyday", no "Enthusiast", no "/month".
  Its entire pitch is the 4-question quiz → curated monthly shipment, with pricing never stated.

So the agent took a bagged-coffee SKU price, relabeled it a monthly subscription rate, extrapolated
a second tier at double, and derived a year's cost ($180 = 12 × $14.99 ≈ correct arithmetic on a
fabricated premise). The arithmetic is internally consistent, which is what makes it dangerous — it
reads entirely plausible.

**Why this is 🔴 and not a content nit:** this is a demo shown to the actual brand. Inventing a
competitor-visible price sheet for a real company is the single highest-risk output class in the
whole pipeline. It is worse than a broken link (finding 13) because nothing *fails* — it renders
beautifully and a reviewer has no signal that the numbers are fiction.

Note the instruction was present and explicit. My dispatch prompt said: "keys include `price` and
`currency` — **use the REAL prices, never invent them**". The agent partially complied (it did source
$3.99/$14.99 from the catalog) and then invented around them. A prompt-level "don't invent" is
demonstrably insufficient.

**Recommended, in priority order:**
1. `of1-build-templates` (budget intent especially) must **assert every price string against
   `products.json`** before writing a sample file — a mechanical check, not a judgment call. Any
   price not in the catalog fails the step.
2. Prices that are *derived* (per-cup, annualized) must be labeled as derived and shown with their
   basis, or omitted. `$0.50/cup` from "a bag makes about 30 cups" is an invented cup-count too.
3. When a demo focus (`narrative.json.focus` = the MyBarista subscription) has **no priced product
   backing it**, that's a finding the pipeline should surface to the user, not paper over. The right
   move here was to build budget templates around real bagged-coffee/pod/machine prices, or to report
   that the subscription has no public pricing.

**Action taken this run:** rewritten to use only catalog-verifiable prices (see below). Flagged to
the user, since the fabricated version was already on disk and would otherwise have reached
`assemble` → commit → the review gallery.

### The deep-dive agent shows the failure was avoidable

Same fan-out, same prompt template, same model — but I audited `of1-deep-dive-longform.sample.json`
against the live `/sustainability` page and **every single claim traced back to real copy**: "modular,
replaceable components", "designed for repair rather than disposal", "honest reporting and realistic
goals", "continuous improvement", "long-term supplier relationships", "stable buying commitments",
"coffee houses", store-level waste/energy. Twelve for twelve. It even preserved the real quote
verbatim, where the budget agent appended a fabricated clause ("…and how we keep prices honest") to
that same sentence.

So the difference isn't capability. **The deep-dive agent had a rich, quotable source page to ground
in; the budget agent's subject — subscription pricing — had no source at all.** When grounding exists,
these agents use it faithfully. When it's absent, they fill the vacuum rather than reporting the gap.

That's the real lesson for the skill: the guard shouldn't be "try harder not to invent". It should be
**"if the grounding for this intent doesn't exist, say so and stop"** — which is why action item 34
(surface unbacked focus areas) matters as much as the mechanical price assert in 32. An intent with no
factual substrate is a pipeline-level finding, not a content-generation problem.

Corroborating detail: all 22 unique image URLs across all 15 templates return 200 — the agents were
reliable on everything mechanically checkable. The failure was confined to the one area where no
check, and no source, existed.

## 🟠 6e. `of1-publish`'s playwright-cli syntax does not match the installed binary

Checks 1 and 2 in `of1-publish` SKILL.md use a `playwright-cli` interface the installed binary
(`/opt/homebrew/bin/playwright-cli`, `@playwright/cli`) does not accept. Two distinct breaks:

| SKILL.md says | Installed binary requires | Failure mode |
|---|---|---|
| `screenshot --fullPage=true` | `--full-page` (name differs, and it **rejects** `=value` on booleans: *"boolean option '--full-page' should not be passed with '=value'"*) | hard error, visible |
| `eval "document.querySelector('header .header') ? 'header OK' : '…'"` | `eval "() => ({...})"` — a function form | **silent empty output** |

The second is the dangerous one. A bare expression produces no result and no error — the check
appears to run and prints nothing. Read casually in a transcript, five blank `eval` lines look like
five checks that found nothing wrong. Both checks were re-run with corrected syntax and **passed
cleanly** (`header:true, navLinks:10, footer:true, footerText:629, of1Block:true, inputs:1, chips:6,
h1:"What can we help you find?"`), so this is a skill-text defect, not a product defect.

The SKILL.md line *"`playwright-cli` calls use `open` + `--fullPage=true` + `--filename`
(SLICC-native syntax; CC shim passes through unchanged)"* is the root cause: the CC shim did **not**
translate — it passed through to a binary with a different interface. "Passes through unchanged" is
only safe if both runtimes' binaries share an interface, and they don't.

**Also:** `--filename` resolves relative to CWD, not `$OF1_STATE_DIR`. A bare relative path silently
wrote nothing findable; an absolute path was required.

## 🟡 6g. Friendly `/media/product-*` URLs are 301s, so naive image checks mislead

## 🔴 6j. `of1-adopt-existing-site`'s delegation model is structurally impossible

The orchestrator states a **HARD RULE: do NOT re-implement steps 6–12 here. Stage 3 is a single
delegation to `of1-adopt-existing-site`.** But adopt-site's own design fans out steps 6a–6e in
parallel — and **subagents cannot dispatch subagents** (the Agent tool is withheld one level down).

The specified architecture therefore cannot run as written: adopt-site, dispatched as an Agent, has no
way to fan out its sub-steps. The orchestrator had to absorb the entire fan-out **plus** steps 11 and
12 inline — violating the HARD RULE in order to complete the pipeline. The user spotted this early
("Can the sub agent start other sub agent?") and chose "I take over the fan-out".

This is the highest-leverage structural finding in the run: two skills' contracts are mutually
unsatisfiable, and the only runtime resolution is for the orchestrator to disobey one. (Item 2 already
names the nesting contradiction; this documents that it *forces* a contract violation, not just
awkwardness.)

## 🟠 6k. Step 6-assemble's git contract collides with the project's own review flow

`of1-build-templates` assemble mode instructs `git push origin "$BRANCH"` where `BRANCH=main`, but the
project's `AGENTS.md` documents a feature-branch → PR → human-review flow. The permission classifier
blocked the push; the subagent could not obtain user consent from its own context, so it stopped with
all work committed locally and escalated.

The subagent handled this **correctly** — it did not force-push, try alternate remotes, or branch
around the denial, and it explicitly asked rather than assuming. It did, however, ask the orchestrator
to run the denied action on its behalf, which is permission laundering and was refused; the
orchestrator surfaced the decision to the user, who authorized the direct push.

Worth noting as a skill defect regardless of the good handling: a production-affecting push should not
first surface as a mid-pipeline permission denial. Either push to a feature branch and open a PR, or
capture explicit direct-to-main consent in phase 0 and pass that authorization down.

### A methodological note on my own checks

Two of my verification passes were themselves buggy, and both failed in the *dangerous* direction —
toward false confidence:

1. My price-provenance check extracted "real" prices only from **string** fields matching `$N.NN`,
   but `products.json` stores them as **numbers** (`"price": 14.99`). The catalog set was therefore
   incomplete, and the check flagged legitimate `$14.99`/`$3.99` as fabricated. Recoverable —
   false positives get investigated.
2. My first image check used `curl -L`, which followed the `/media/product-*` 301s silently and
   reported "all 22 images 200" (see 6g). **Not** recoverable by inspection — it produced a clean
   pass that concealed the redirect layer entirely.
3. My first fabrication sweep scanned only `sample.json` files, missing that the same invented prices
   were **also** baked into the `.html` slot defaults and the catalog's embedded `htmlContent`. The
   CDN was still serving `$29.99 / month` after I had "fixed" the pricing.

The general lesson for whoever hardens these skills: **a check that can only pass or silently
under-report is worse than no check**, because it converts an unknown into a false known. Every assert
added for items 32/36/37 should be tested against a deliberately-bad fixture to prove it can actually
fail.

- **Stage 1 (`of1-discover-narrative`) was excellent.** Picked the MyBarista subscription as the
  demo spine — genuinely the site's own headline story — and produced a rich `tone` field.
- **Its page-exclusion reasoning was the standout.** It verified every candidate returns 200 *and*
  proactively excluded `/coffee`, `/machines`, `/quiz` as Commerce-dropin GraphQL renders with no
  server HTML, plus `/tea` as a live 404 despite being in the nav — recording a per-page `reason`.
  That's exactly the class of failure that otherwise burns a downstream stage on a fidelity-gate
  retry. The `excludedPages` array should be treated as a first-class contract and passed to every
  downstream stage.
- **Per-step status files made the mid-flight abort cheap** — step 8a's output survived the Stage 3
  kill intact and was reused as-is.
- `verify.sh` itself is well-structured; the ok/warn/fail + `RESULT:` summary made the two real
  blockers obvious at a glance once detection was fixed.
